Product Review

What's between this and a real SaaS product

Barber AI Receptionist — n8n workflow (118 nodes, live) + React dashboard + Supabase. Reviewed against the actual code and database on 1 August 2026.

Short version: you have a working product for one barbershop. It books, reschedules, cancels, syncs to calendar, emails, and texts. All of that is verified working end to end.

What you don't have is a second barbershop. Not "it needs polish" — there is currently no mechanism by which shop #2 could exist. Every shop-specific value in the system is a constant, and the database has no column anywhere that says which shop a row belongs to.

The Twilio number you flagged is a real gap, and it's the right instinct, but it's one of five things wired the same way. Fix it alone and you still can't onboard a customer.

Added after seeing the Dograh screenshots: the voice agent is currently pointed at a Railway app that no longer exists, so right now every phone call fails. That's section 00 below and it outranks everything else on this page.

Same root cause

The agent advertises a waitlist the workflow can't handle

Silent dead end

The Agent Node prompt says it handles "joining the waiting list", and the tool exposes four waitlist parameters (waitlist_date_from, waitlist_date_to, waitlist_time_window, any_barber). The workflow contains zero references to any of them, and has no waitlist route.

A caller asking to join the waitlist falls through to the default booking_stub branch. The barber_waitlist table exists and the dashboard has a Waitlist page, so the two ends are built and the middle is missing. Either add the route or remove the promise, but don't ship it half-connected.

The 5 second timeout is too tight

Will fail intermittently

Tool timeout is set to 5000 ms. A simple availability check already takes about 2.5 s. A real booking does strictly more work on the same request: shop fetch, overlap check, Supabase insert, Google Calendar create, then an ID patch back. That is comfortably within range of 5 s on a slow day.

When it trips, the caller has already heard "Let me check that for you, one moment please" and then gets nothing, while the booking may well have been created anyway. Raise it to 15 s, and make the flow idempotent so a retry can't double-book.

Two things in this UI solve problems from later in this report

Use these

Preset Parameters inject values the model never sees. That is exactly the right channel for the shop_id that section 01 says you need, and for a shared secret that fixes the unauthenticated webhook in section 04. Both without touching the LLM-facing schema.

{{initial_context.phone_number}} means you already have the caller's number from caller ID. Today phone is a parameter the model has to ask for and transcribe, which is the single most error-prone thing in a voice booking flow. Preset it and stop asking.

There is also an unused Authentication tab on this tool, which is where the webhook secret belongs.

01

The blocker: there is no concept of a tenant

I checked all 13 tables for any tenant-scoping column (shop_id, tenant_id, org_id, account_id). There are none. shop_config holds exactly one row and the dashboard reads it with .single(), which errors if a second row ever appears.

So today, "the shop" is not data. It's the shape of the deployment. Adding a customer means cloning the whole stack: new Supabase project, new n8n workflow, new credentials, new deploy. That is a consulting business with software attached, not a SaaS. It caps you at roughly as many clients as you can hand-configure, and every bug fix has to be applied N times.

How I verified Queried information_schema.columns across the public schema for tenant-shaped column names. Zero matches. shop_config row count: 1.

This is the one item that has to be decided before almost anything else on this page, because it changes the shape of every other fix.

03

The Twilio number, from both sides

You singled this out, so it's worth going deeper than one table row. There are two separate problems bundled together: provisioning (each shop needs its own number) and the number you're currently using is the wrong kind of number.

Developer perspective

Not built

Provisioning is an API call, not a manual step. Twilio's IncomingPhoneNumbers endpoint can search available numbers by country and area code and purchase one in a single flow. The pieces you'd need:

  • Columns on the shop row: twilio_number_e164, twilio_number_sid, twilio_subaccount_sid.
  • A provisioning step in onboarding that buys a number and stores the SID.
  • Change the 4 SMS nodes from a literal from to an expression reading the shop's number.
  • Inbound routing. This is the part that's easy to forget. When a customer replies to a text or calls the number back, the webhook fires with a To field. You look up which shop owns that number and route accordingly. Without this, replies vanish.
  • A release path on churn, so you stop paying for numbers of cancelled customers.

Twilio subaccounts are worth considering: they isolate each shop's usage, logs, and spend, which makes both per-tenant billing and debugging significantly easier than one flat account.

Barber / customer perspective (US market)

Needs area-code matching

The sending number +1 762 744 5951 is a Georgia number, so for a US product the country is right. What's wrong is that it's one number for everybody. From the chair:

  • A customer in Phoenix gets a confirmation from a Georgia area code. Americans read unfamiliar area codes as spam, and answer rates on callbacks drop hard.
  • If they reply or call back, nothing routes to their shop.
  • Local presence is the whole point. Provision each shop a number in its own area code, taken from the shop's address during onboarding. Twilio's number search accepts an area code filter, so this is a parameter, not extra work.

Good news for US: no regulatory address bundle is required for domestic numbers, unlike most of Europe. The hard requirement is A2P 10DLC registration instead, which is section 3b below.

Also worth pricing: a US local number is roughly $1.15/month standing cost per shop before a single message is sent, plus per-message fees and 10DLC campaign costs. Multiply by tenant count and it becomes a real cost of goods line your pricing has to cover. Right now nothing in the system tracks per-shop messaging spend.

3b

Selling into the US changes three things

You mentioned after I wrote the first draft that this is built for the US market, not the UK. That corrects the Twilio section above and adds the following, one of which is a hard legal gate.

A2P 10DLC registration is mandatory, and it shapes your architecture

Hard gate

US carriers require every application-to-person SMS sender on a local 10-digit number to be registered: a Brand (the business) and a Campaign (what you send). Unregistered traffic is filtered or blocked outright, and the failure mode is silent. Messages report as sent and never arrive.

The part that affects design: whose brand is it? Two models, and you should pick now.

  • Each shop registers itself. Cleanest deliverability and highest trust, but every customer needs an EIN and has to complete registration before they can send. That is friction in onboarding measured in days, and small barbershops will stall on it.
  • You register as an ISV / reseller and create sub-brands per customer under your own account. Much faster onboarding, and it's what most vertical SaaS products do. More setup for you up front and you carry responsibility for what tenants send.

Either way there are per-brand and per-campaign fees, so this belongs in your unit economics alongside the number rental. Toll-free numbers are an alternative with their own mandatory verification process, and they carry no local-presence benefit, so for a barbershop local 10DLC is the better fit.

Practical consequence: onboarding cannot be "sign up and start taking calls in 5 minutes" for SMS. Design the flow so a shop can go live on voice and email immediately, with texting switching on once registration clears.

TCPA exposure, particularly on the features I suggested

Legal

The US regulates automated calls and texts far more aggressively than the UK, with statutory damages per message and an active plaintiffs' bar. Rough shape of it:

  • Appointment confirmations and reminders the customer asked for are transactional and low risk.
  • The win-back campaign idea in section 08 is marketing. That needs prior express written consent, captured and logged, before you send a single one. Build the consent field before you build the feature.
  • STOP / HELP keyword handling is required, and opt-outs must persist. Nothing in the schema currently records consent or opt-out state. That's a column on clients you don't have yet.
  • Quiet hours are generally 8am–9pm in the recipient's timezone, which is another reason the timezone problem below is not cosmetic.

Call recording consent varies by state

Legal

Dograh has a Recordings section, so this applies if you retain call audio. Most US states are one-party consent, but a significant set including California, Florida, Illinois, Pennsylvania and Washington require all-party consent. A shop in Los Angeles recording calls without a disclosure is exposed in a way the same shop in Texas is not.

The safe pattern is a recording disclosure in the opening greeting for every call, which the Global Node is already the natural place for. Cheap to add now, expensive to retrofit after a complaint.

04

Two security issues to fix before you sell this

The booking webhook has no authentication

Confirmed

The n8n webhook at /webhook/skyweb-barber-basic accepts unauthenticated POSTs from anywhere on the internet. I'm confident about this because I used it that way during testing: the two bookings I created earlier in this session were plain curl calls with no credentials of any kind.

Anyone who learns the URL can create, reschedule, or cancel real bookings, and cancellation only needs a phone number to match. Fix with a shared secret header that Vapi sends and the workflow checks, or Twilio/Vapi signature validation.

Row Level Security is enabled but permissive

Confirmed

RLS is on for all 13 tables, which looks reassuring, but several policies are USING (true). Specifically anon_write_appointments is ALL … USING (true), meaning anyone holding the public anon key (which ships in your frontend bundle by design) can read, modify, or delete any appointment row.

Single-tenant this is bad. Multi-tenant it's fatal: it becomes read access to every competitor shop's full customer list, phone numbers included. When you add shop_id, every policy needs rewriting to scope by the caller's shop rather than true.

05

No way for a customer to become a customer

There's no signup. Login.jsx is sign-in only, against manually created Supabase auth users. There's no shop provisioning, no trial, no plan selection, no payment.

The billing scaffolding is further along than I expected and deserves credit: usage_packages exists with included calls, included minutes, cap mode, overage rates and monthly price, and PackageSettings.jsx gives an operator a UI to edit it. Usage.jsx renders consumption meters that turn amber at 75% and red at 90%.

But it is entirely descriptive. Nothing charges a card, nothing enforces a cap when it's hit, and the numbers are typed in by hand. It's the shape of a billing system with no billing system behind it. Connecting Stripe to what's already modelled here is a comparatively small job, and it's the step that turns this from a project into a business.

What you've already built well

Worth stating plainly, because the list above is relentlessly negative and the foundation is genuinely good.

The booking engine

Verified live

Book, reschedule, cancel, walk-in, lookup, availability, FAQ, and human-handoff intents all route correctly. Overlap detection, alternative-slot suggestion, and minimum-notice rules work. Phone normalisation to E.164 is handled at the database layer, which is the right place for it.

Operational depth

Unusual for this stage

Waitlist with slot offers, barber time-off with an email-driven day-off flow that finds and cancels affected bookings, a notification outbox, call logs, and an Automation Health page showing whether the pipeline is alive. Most products at this stage have none of this.

Graceful degradation

Thoughtful

The configDegraded flag is a genuinely good piece of design. If shop data fails to load, the assistant falls back to empty values rather than impersonating another business, and it surfaces the failure instead of hiding it. That's a mistake most people only learn to avoid after making it in production.

Role model

Solid start

Three roles (operator / admin / barber) with a barbers_no_self_promote policy preventing privilege escalation. The operator tier is exactly the right abstraction for a future SaaS vendor-vs-customer split.

08

Additional features worth considering

None of this is required to ship. It's what would make the product harder to leave, listed roughly by how much barbers actually complain about the underlying problem.

Deposits & no-show protection

High value

No-shows are the single biggest revenue leak in this trade. Card-on-file at booking with a configurable late-cancel fee, plus a no-show counter per client, would justify the subscription on its own for most shops.

Customer self-serve booking page

High value

You already have availability logic, services, barbers and hours. A public booking page reusing it is mostly presentation work, and it captures customers who won't phone.

Automated review requests

High value

Text a Google review link two hours after the appointment. Trivial to add to the existing notification outbox, and local search ranking is the thing barbershops care most about.

Win-back campaigns

Medium

You know a client's typical interval. If someone's two weeks overdue, text them an offer. The clients table already exists and is currently empty and unused. US caveat: this is marketing, not transactional, so it needs logged prior express written consent under TCPA. Build the consent capture first (section 3b).

Barber-facing mobile view

Medium

The dashboard already responds down to mobile widths. A PWA with push notifications for new bookings would make it feel like a real product rather than a website.

Multi-location groups

Later

Chains are where the money is, but design for it now: make shop_id nest under an optional organisation_id from day one. Retrofitting that later is painful.

Analytics the owner cares about

Medium

Revenue per barber, busiest hours, no-show rate, calls answered versus missed, new versus returning. The data is all being captured already; nothing surfaces it.

White-label branding

Cheap

Logo, colour and shop name per tenant. shop_config already has logo_url and the design system is fully tokenised, so this is close to free.

09

One strategic call to make first

Before writing any of the above, decide between two paths, because they lead to different codebases:

Pooled multi-tenant. One Supabase project, one n8n workflow, shop_id everywhere, RLS doing the isolation. Cheap per tenant, one deploy, one fix applies to everyone. It's the standard SaaS answer and it's what the roadmap above assumes. The cost is that an RLS mistake is a cross-customer data breach, so the policies have to be right.

Instance per tenant. Keep cloning the stack. Isolation is total and it needs no rewrite, so it's tempting. But cost and operational load scale linearly, upgrades have to be applied N times, and it stops being viable somewhere around ten customers.

Given the workflow is already one artefact serving one shop, pooled is the right call, and the sooner you commit the less there is to migrate. Roughly a week of schema and RLS work now saves a rewrite at customer fifteen.
